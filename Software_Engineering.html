Engineering

I like working on problems where the code is only part of the solution. Some of the projects I've enjoyed most have involved figuring out how software behaves once it leaves a development machine — whether that means running across cloud nodes, communicating over a network, processing simulation data, or operating alongside hardware with limited resources.

How I approach engineering

I like understanding the whole system.

My engineering experience has taken me through software development, systems engineering, cloud infrastructure, networking, AI, and hardware/software integration. I don't really see those as isolated areas. In the projects I've worked on, they tend to overlap.

A program might work perfectly on a development machine and still fail once it has to communicate with another system. A model might produce useful results but require an entirely different deployment strategy when it has to run on limited hardware. A pipeline might produce the right numbers but still be difficult to use if the results aren't presented clearly.

Those problems are what I find interesting. I enjoy tracing an issue through the layers of a system, figuring out where the actual constraint is, and building something that is practical enough to work outside of the lab.

Campus Connect • 2025

Building a student-focused platform from the ground up

Campus Connect was one of the projects where a lot of my interests came together. The idea was essentially a Discord-like platform built around students: users could sign in, communicate through live messaging, and upload files that could then be used as a source of information for AI-powered features.

The interesting part wasn't just building the interface. We had to make the different pieces of the application work together. I worked with React on the front end and FastAPI on the back end, while the supporting services were distributed across cloud nodes. This gave me practical experience with the difference between building something locally and actually deploying a system made up of multiple services.

We also built several RAG-based features as part of the project. One implementation used an Ollama-hosted model on one cloud node, a ChromaDB instance and embedding model on another, and FastAPI to connect those services to the application. The uploaded information had to be pre-processed and chunked before being embedded and retrieved.

Another part of the project used Bluesky API data to build a dataset for the system. We also experimented with synthetic syllabus information for a "teacher" bot aimed at helping students interact with course material. Rather than treating RAG as a single feature, working on these variations taught me how much of the work happens before a language model ever receives a prompt.

Edge Computing / Computer Vision

An image codec designed for constrained environments

Another project took me in a very different direction. I worked on an edge-optimized image codec intended for environments where bandwidth and compute resources matter. The goal was to explore whether learned image compression could provide useful image quality while reducing the amount of data that needed to be transmitted.

The target architecture involved a Raspberry Pi 5 acting as the constrained encoder and a Jetson device handling decoding. Because I didn't have the exact target hardware available for every stage of development, I also worked with constrained containerized environments to reproduce some of those limitations.

The networking side became just as interesting as the compression itself. I developed a UDP-based transfer approach for the encoded binary data, including packet sequencing and reassembly. Debugging the system forced me to look beyond whether the file arrived and ask whether every byte was being interpreted correctly by the decoder.

That project taught me a lot about the difference between a component working in isolation and a complete system working end to end. Compression performance, CPU limitations, serialization, networking, and image reconstruction all had to be considered together.

NASA LUCY Mission • Systems Engineering

Turning simulation data into something engineers could use

My work connected software development with systems engineering through NASA's LUCY Mission. One of the projects I worked on involved building an end-to-end pipeline for simulation data.

The pipeline took simulation output, processed the data, analyzed it, and produced plots that could be used to understand the behavior of the system. The work didn't stop at visualization, though. Part of the process involved identifying and correcting the data for relevant physics properties so that the resulting information could be interpreted appropriately.

I enjoyed this work because it was a good example of why engineering software needs to be built around the problem it is solving. The important question wasn't simply whether the code could read a dataset. The useful question was whether the complete pipeline could turn raw simulation output into information that an engineer could actually reason about.

L'SPACE Program • 2026

Engineering is also about making a team work

Through the L'SPACE program, I had the opportunity to work on a mission-oriented engineering problem rather than a traditional software project. I led a team of eight engineers while we developed and presented a lunar surface vehicle concept.

That experience pushed me outside of the purely technical side of engineering. Requirements, design decisions, documentation, presentations, and coordination all had to stay aligned. I learned that a technically strong solution isn't particularly useful if the team cannot explain it, document it, or agree on how it should be developed.

It also reinforced something I've encountered throughout my other projects: engineering is usually a collaborative process. Writing the code is important, but understanding the requirements and communicating why a decision was made can be just as important.
